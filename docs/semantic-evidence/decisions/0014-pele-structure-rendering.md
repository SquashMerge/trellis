# Decision 0014: generated Mermaid and Pele for structure views

- **Status:** owner-approved 2026-10-20 (#182); ratified when this record and the matching `SPEC.md` amendment merge together. This is a rendering direction, not authorization to replace existing views or start a Factory run.
- **Amends:** `../../../SPEC.md` §1 (authoring direction), §3 (renderer choices), §9 (rendering and layout), and §11 (later diagram-to-code workflow). The indexed evidence, source reads, request queue and storage contracts are unchanged.
- **Compatibility:** no pinned diagram positions. A diagram may move after re-indexing; selected source identity and revision checks must still hold.

## Decision

1. **Rendering target.** Generate Mermaid text from the authoritative, revision-bound structure DTO and render it with a locally served, exact-version-pinned Pele asset. This is the target for structure views, not a claim that all seven proposed types already have measured DTOs or are scheduled. Migrate one view at a time, starting with a read-only sequence slice; class, ERD, event, state, C4 and treemap views need their own scoped acceptance. Mermaid text can also be exported, but rendering does not promote syntax guesses or agent-authored diagrams to measured evidence.
2. **Parity before replacement.** Keep each current view usable until its replacement preserves the existing evidence semantics and navigation: measured call order and control structure, explicit unknown/partial states, source detail, collapse/expand, keyboard use, and revision-bound click-to-source. Never invent a target, dispatch, runtime trace, return, activation duration or alternate path because Pele can draw one. A view that cannot represent an admitted DTO faithfully must fail visibly or keep its current renderer; no silent dropped evidence. Remove old SVG only after the replacement's parity tests pass.
3. **No pinned layout.** Layout positions may change after re-indexing. Preserve selected symbols/calls and snapshot-bound source actions, not canvas coordinates. Keep bounded, scoped expansion and visible truncation.
4. **Element identity and untrusted text.** Pele 1.6.0's prototype emitted positional sequence-note `data-id` values, but not a native ID on an `alt` frame. These are renderer details, **not** Trellis IDs. Pin and test the chosen version's actual output, maintain a separate mapping from rendered elements to measured source IDs/ranges, and fail closed on an unexpected element/order change. Render repository labels as untrusted text, keep options under app control, bound input/output/work, and display parse/render errors using `textContent`. Apply `DESIGN.md` tokens and current browser safety rules. The loopback asset size is acceptable to the owner; still record actual deployed bytes and browser load/render costs.
5. **Later editing direction, not scheduled.** A user may later edit Mermaid text directly or with GUI controls over that text. Compare its *structure*, not whitespace or layout, to the revision-bound generated model; treat the difference as user-proposed intent with stable source references and hand a structured change request to an agent. Trellis does not directly edit repository code. The agent's changes are inspected, explicitly approved where required, and verified by re-indexing and comparing measured state to the proposal. This decision does not define a wire schema, ship editing, or schedule Phases 2–3. Phase 1 remains read-only.

## Feasibility boundary and follow-on

The scratch Pele 1.6.0 probe for #182 reconstructed one real indexed Rust sequence DTO from an isolated copied source file at the CLI-published revision. It rendered six calls and one conditional without fabricated arrows. A Chrome click on a native note `data-id="i2"` resolved through a separately assigned source-step ID to the exact `src/behavior_js.rs` call bytes; the `alt` frame lacked a native ID. This probe **did not read the published Store snapshot** and did not preserve all existing sequence interactions. Its ~256 KB gzip JS and tiny-DTO rendering time are feasibility evidence, not a production performance or parity result. The first implementation slice must include a published-read regression, tested positional mapping including frames, full-current-view parity and normal-size browser checks. Until then #182 remains a proposal, not a factory-ready seven-view feature.

The block fix measures repeated/opposite labels within an unordered endpoint pair and routes affected native edges through their final label centers. Native identities and deterministic output remain required; native route coordinates may change. It is not a global label or node-obstacle solver. Exact output and native browser click regressions live under `tests/fixtures/pele-1.10.0-trellis.2/` and `tests/browser/pele-block-labels.test.cjs`; Sequence and representative frozen output remains unchanged. No app-side route workaround, semantic binding, DTO or persistence expansion is authorized by this amendment. Architecture #310 is a separate implementation and PR.
