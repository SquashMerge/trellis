# Manual metrics benchmark (not a CI gate)

This measures `metrics:v1` over the complete canonical synthetic medium and large cohorts. The runner rejects partial, failed, timed-out, or malformed responses. It times wall-clock time from request start until the **entire** response is received and JSON parsed. HTTP `responseBytes` counts the exact received body bytes; CLI `responseBytes` counts the complete `--json` stdout bytes (pretty-printed, so it differs from HTTP). Indexing and server startup are recorded separately and are not part of the metric timings. No measured timings are written into the metric payload.

Run from the Trellis checkout on macOS or Linux with Python 3, Node.js, Rust 1.99 and the normal native build prerequisites. Use a new temporary output directory with enough space for approximately 180 MiB of generated source plus two independent indexes and logs. The generator writes `small` too; neither benchmark selects it. Replacing the temporary paths below is safe. Keep **one runner at a time** so only one checkout/daemon is under measurement; `--output-dir` must be the same existing parent for all four calls, The default HTTP calls create new homes; the CLI calls below reuse each HTTP index only after that home’s daemon has stopped. Do not rerun a pair without removing its external results. The runner verifies the expected source-file count before indexing.

```sh
export RUSTUP_TOOLCHAIN=1.99
export CARGO_TARGET_DIR=/tmp/trellis-factory-120-bench-target
mkdir -p /tmp/trellis-factory-120-metrics-bench
node tools/synthetic-cohorts/generate.mjs --out /tmp/trellis-factory-120-metrics-bench/generated
cargo build --locked --bin trellis
python3 tools/metrics-bench/run.py --binary "$CARGO_TARGET_DIR/debug/trellis" --cohort medium --transport http --generated /tmp/trellis-factory-120-metrics-bench/generated --output-dir /tmp/trellis-factory-120-metrics-bench/results
# Observe the medium HTTP pin in results/medium-http.jsonl, stop that home's
# daemon (see below), then pass that exact pin to the CLI runner:
python3 tools/metrics-bench/run.py --binary "$CARGO_TARGET_DIR/debug/trellis" --cohort medium --transport cli --generated /tmp/trellis-factory-120-metrics-bench/generated --output-dir /tmp/trellis-factory-120-metrics-bench/results --reuse-home /tmp/trellis-factory-120-metrics-bench/results/medium-http-home --pin '<medium-generation>:<medium-revision>'
python3 tools/metrics-bench/run.py --binary "$CARGO_TARGET_DIR/debug/trellis" --cohort large --transport http --generated /tmp/trellis-factory-120-metrics-bench/generated --output-dir /tmp/trellis-factory-120-metrics-bench/results
# After large HTTP exits, stop only its daemon and reuse its recorded pin:
python3 tools/metrics-bench/run.py --binary "$CARGO_TARGET_DIR/debug/trellis" --cohort large --transport cli --generated /tmp/trellis-factory-120-metrics-bench/generated --output-dir /tmp/trellis-factory-120-metrics-bench/results --reuse-home /tmp/trellis-factory-120-metrics-bench/results/large-http-home --pin '<large-generation>:<large-revision>'
```

The runner starts `trellis serve --workspace <generated>/<size> --bind 127.0.0.1:0 --token-file <external-token>`; it discovers the selected `rootKey` via authenticated `GET /api/checkouts`, enqueues `POST /api/checkouts/{rootKey}/index`, then waits for the completed job through `GET /api/checkouts/{rootKey}/jobs/{id}`. This avoids the CLI index command’s separate 60-second synchronous wait, which can expire during canonical-cohort indexing. Each HTTP cohort has a separate private temporary `HOME`, index and daemon. The CLI reuse invocation uses the **same** index and pin after that daemon has exited, but starts a new daemon with an empty source-only metrics memo. Identify the daemon PID using `lsof -t '<home>/Library/Application Support/dev.squashmerge.trellis/run/daemon.lock'` on macOS (Linux: `<home>/.local/share/trellis/run/daemon.lock`), verify the PID's executable with `ps -p <pid> -o command`, then `kill -TERM <pid>` and verify it has exited **after** the HTTP runner has stopped its serve control process. Never signal a daemon while a request is active. Indexing does not fill the metrics memo. The first default `revision` HTTP request is cold; CLI's first request supplies the reused explicit pin and is cold on its restarted daemon. The second is the **same pin**, with no intervening indexing, on the same daemon and is warm. For HTTP these are authenticated `GET /api/checkouts/{rootKey}/metrics` then `GET` with `indexGeneration` and `indexRevision`. For CLI they are `trellis metrics --json --workspace <root> --pin <generation>:<revision>` then `trellis metrics --json --workspace <root> --pin <generation>:<revision>`. No metric selection or aggregate override is supplied: all 12 metrics and `sum` apply. A separate pinned `file` request for a Java row follows and must include declaration rows.

Records are appended to `<output-dir>/<size>-<transport>.jsonl` as each stage completes. `validFullResponse` requires all 1,000 or 10,000 file rows, a root directory row, no declaration rows for revision, and all 12 selected metrics. `directoryRows` must also match the report below; any discrepancy is a failed run, not a substitute measurement. `callablesComputed` sums all file `declarationCount` fields. Typed HTTP failures retain status and parsed error in `typedError`; CLI failures retain exit, stderr, and parsed error. A client-side timeout records partial bytes but never reports a successful measurement. The runner has a 335-second client backstop; the daemon's revision work deadline is 300 seconds and the serialized metrics response bound is 64 MiB. On a timeout or `response_too_large`, stop and seek an owner ruling. The response-size bound does not make an over-limit reply into a valid full DTO.

See [the dated measurement](2026-10-18.md) for observed data. No automated performance threshold is added.
